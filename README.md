# Batchlabel — product app

`app.batchlabel.xyz`. The product, and all account management including buying a
plan. `www.batchlabel.xyz` (repo `batch-label`) is marketing plus auth, and hosts
the server side of billing — the Stripe secret key and the plan contract live
there and cannot be in a browser bundle.

**No price and no allowance is written in this repo.** They come from
`GET /api/plans` on the marketing origin, which is generated from the same plan
contract the Stripe prices are created from. When that request fails, `/billing`
says so and shows nothing. There is no fallback table and there must not be one.

Originally generated by [Magic Patterns](https://magicpatterns.com) from
[this design](https://www.magicpatterns.com/c/b1fc7jx5cxx7jayewgpyr5).

## Getting started

1. `npm install`
2. `cp .env.example .env.local` and fill in `VITE_SUPABASE_ANON_KEY`
3. `npm run dev`

Without the Supabase variables the app renders a "sign in is not configured"
screen rather than the product. That is deliberate — see the integration guide.

## Read this before touching auth or billing

**[`docs/INTEGRATION.md`](docs/INTEGRATION.md)** — how the two sites share one
login, the byte-for-byte duplication rule on `src/lib/session-storage.ts`, the
entitlement read contract, the billing calls, the environment variables, and what
has to be configured in Supabase, Vercel and Stripe.

Three short versions:

- `src/lib/session-storage.ts` is duplicated verbatim from the marketing repo. Do
  not edit it here alone.
- Entitlement is `public.entitlements.active`, decided by
  `public.entitlement_is_active()` in the database. Read it; do not reimplement
  it. This app once had its own copy of that rule and disagreed with the database
  three ways, all of them in the direction of giving the paid product away.
- `/billing` and `/billing/success` are the URLs Stripe returns customers to.
  Renaming either strands somebody on a 404 immediately after they have paid.
